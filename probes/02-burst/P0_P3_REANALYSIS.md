# P0/P3 回传再分析（2026-10-29）

对象：Z6 II v1.70 冷启动 stock（guest 2.5 s）　输入：`.local/webui/probe/` 的 dump + `P0_P3_REPORT.md`

## 0. 根因：mas 运行期基址是 0x10020000，不是 0x10000000

- `memsave` 在 `0x10020000` 读出 mas 头 `20 2f 00 ea`；`0x1032CC66` 的代码与 mas 文件 `0x30CC66` 逐字节相同。
- 因此所有静态 VMA 在运行期都要 **+0x20000**。
- 主线之前 dump 的四个地址都低了 0x20000：
  - `0x1242E7A0`（应为 `0x1244E7A0` 的 60 条任务描述表；实际读到的是一张 16 字节对象表的尾部）
  - `0x119DF50C`（应为 `0x119FF50C` 的 6 条模式记录）
  - `0x1092CF50`（应为 `0x1094CF50` 的 mas 视频表；原地址是 0xF1 填充）
  - `0x109417B8`（应为 `0x109617B8` 的完整尺寸表）
- **工具口径**：后续统一用 HMP `memsave <vaddr> <size> <file>`，不要用 QMP `pmemsave`。

## 1. 名字表结构

### 1.1 组件/服务名表 `0x1244C224`

- 步长 **0x18**：20 字节名字 + u32 层级 ID。
- 例：`CaptureSensorService=0x02020000`、`CaptureComponent=0x03040000`、`CaptureService=0x04170000`、`CaptureSequenceService=0x04210000`、`SifDriver=0x41090000`、`SifService=0x421D0000`。
- 这张表是**服务/驱动注册名**，不是任务入口表。

### 1.2 任务描述表 `0x1244E7A0`

- 步长 **0x1C**：`name[12] + u32 type + u32 size + u32 0x1000 + u32 0`，共 60 条。
- `CAPSEQ`=索引 52、`CAPTG`=53、`SHUTTER`=54；`STGRAW`=21。
- 最后 4 字节静态全 0；本轮 dump 也没有入口指针。
- 名字段与 mas 文件 `0x242E7A0` 完全相同（只是整体 +0x20000）。

### 1.3 运行期对象注册表 `0x1242E4D0..0x1242E820`

- 步长 **0x10**：`(u32 owner=1, u32 0, u32 heap_ptr, u32 id)`。
- 共 53 条，ID 从 `0x530` 到 `0x564`；指针在 `0xc2a49c5c..0xc2a4afb0` 和 `0xc188cc18..0xc188cc48`。
- **主线 dump 的 `0x1242E7A0` 是这张表的尾部**（条目 45–52），不是 60 条任务描述表。它列出的 0–4 条对应：
  - ID `0x55e` → `0xc2a4a858`
  - ID `0x55f..0x564` → `0xc188cc18..0xc188cc40`（8 字节步长）
  - ID `0x53a` → `0xc188cc48`
- 这些是堆对象句柄。堆在 `0xc1xxxxxx`，不在本次 64 MiB dump（`0x10000000..0x14000000`）里，**无法从现有 dump 判断对象类型**。
- 假设：`0xc188cc18..cc48` 是 8 字节的任务/队列句柄；`0xc2a4a858` 是较大的任务对象。CAPTG 不在启动时的 53 条里，可能在进入拍摄模式后才创建。
- **顺序假设**：53 条 = 任务 0..52（`PBPSUB..CAPSEQ`），最后一条 ID `0x53a` 对应 `CAPSEQ`（任务索引 52）。`CAPTG` 是索引 53，启动时未创建；进入 CH / CH extended / Movie 后应新增第 54/55 条（CAPTG/SHUTTER），ID 可能在 `0x565+`。P3 必须在模式切换后再 dump 注册表，用新增条目找 CAPTG 的对象指针。注意 ID 顺序并非严格递增（最后一条是 `0x53a`），所以这是假设，不是已证事实。

## 2. SIF 名字与处理入口

- SIF 名字在 `0x1078B196`，16 字节步长 ×8；`SIF_7` 在 `0x1078B276`，下一个是 `PPC_0` 在 `0x1078B296`。
- **SIF 名字后面没有紧跟 8 个处理指针**；处理入口在 31 项表 `0x1030E634` 的第 12–19 项。
- 该表里存的是**静态地址** `0x1030xxxx`，但运行期代码在 `0x1032xxxx`（已核对 `0x1032CC66`）。说明调度器要么在查表后加 `+0x20000`，要么这张表只是模板。
- 修正后的运行期 P1 入口：
  - SIF_0 `0x1032CC66`
  - SIF_1 `0x1032CBCA`
  - SIF_2 `0x1032CB8E`
  - SIF_3 `0x1032CB18`
  - SIF_4 `0x1032CABE`
  - SIF_5 `0x1032C9C8`
  - SIF_6 `0x1032C882`
  - SIF_7 `0x1032C77E`
- 建议同时加读监视 `0x1030E664..0x1030E684`（表项 12–19）。若命中，记录 PC；这能证明调度器是否使用这张静态表以及是否加 0x20000。

## 3. 修正后的 P4 表

### 3.1 mas 视频表 `0x1094CF50`（18×12）

- 字段：`u16 id, u16 0, u32 fps, u16 w, u16 h`。
- 内容：720×480@60、1280×720@60、1920×1080@60、1080p50、1080p24/25/30、**4K30/25/24**、1080p120/100。
- **没有 4K60**。

### 3.2 SLA 视频表 `0x1091D58C`（16×0x20）

- 这是 4K60 的真实来源（mas 里没有）。
- 记录：`+0x08 u16 w, +0x0A u16 h, +0x0C u32 rate(=fps×1000), +0x10 u16 1001/1000, +0x12 u16 1/3, +0x14 u16 30/24/15/12, +0x18..`。
- 内容：4K60、4K50、4K30、4K25、4K24、1080p60/50/30。
- 这是**编码/输出模式表**，不等于传感器读出窗口；4K60 场景要同时看这张表和 SIF 消息。

### 3.3 尺寸表 `0x109617B8`（6 字节/项）

- 完整表有 14 项：FX 6048×4024、4528×3016、3024×2016、4016×4016、3008×3008、2000×2000、6048×3400、4528×2544、3024×1696、**DX L 3936×2624 (id 9)**、**DX M 2944×1968 (id 10)**、**DX S 1968×1312 (id 11)**、4K 3840×2160 (id 12)、1080 1920×1080 (id 13)。
- 这是**输出几何**，不是读出窗口；不要把它当读出表。

## 4. 模式记录 `0x119FF50C`（6×0x480）

- 每条只有 3–6 个非零 dword：
  - rec0: `0x1c=1, 0x20=2, 0x33c=0x309, 0x344=3, 0x34c=1, 0x350=2`
  - rec1: `0x1e8=1, 0x1ec=2, 0x1f0=3`
  - rec2: `0x88=0x30b, 0x90=2, 0x98=1, 0x3b4=1, 0x3b8=2`
  - rec3: `0x254=0x57b, 0x25c=2, 0x264=1`
  - rec4: `0x100=1, 0x104=2, 0x420=0x57c, 0x428=3, 0x430=1, 0x434=2`
  - rec5: `0x2cc=1, 0x2d0=2, 0x2d4=3`
- **没有宽/高/帧周期字段**；这些是状态/对象 ID，不是参数表。
- P2 仍可在模式切换时监视写入，但不要期待在这里直接看到 3936×2624 或 33.33 ms。

## 5. 对 P2/P5 的结论

- P2（模式记录写监视）和 P5（MMIO 写回退）需要**实际拍摄/快门**才能触发；当前仿真机没有快门脚，**标记为真机探针**。
- 可在仿真机上做的替代：菜单里切换画幅/尺寸/位深/释放模式，观察 SIF 入口、表读、对象注册表是否变化；这属于 P1/P3/P4 的“菜单触发”子集，不等于连拍。

## 6. 需要主线补的 dump

1. `memsave 0xc188c000 0x1000 heap_small.bin`（handle/descriptor 区；已有）
2. `memsave 0xc2a40000 0x10000 heap_arena.bin`（整个 0xC2A4xxxx 对象 arena；启动时 `0xc2a49000` 全 0，说明对象未初始化/服务未启动，不是地址错）
3. 切换一次 DX L / DX M / DX S 后，再 `memsave 0x1242E4D0 0x400 registry_after.bin`，并重 dump `0xc2a40000 0x10000`
4. 若仿真机可进 Movie 模式：分别切 4K30/4K60，dump `0x1091D58C` 0x200 和 `0x119FF50C` 0x1B00

registry → handle → object 是两级：注册表指向 `0xC188CC18..cc48` 的 handle，handle 里再存对象指针（如 `0xC2A4AAB8`）。所以 `0xC2A49000` 全 0 不等于 registry 错，需要看 handle 和对象 arena 的初始化时机。若模式切换后 arena 仍全 0，跑一次 `xp /16x 0xC2A4A858` 检查是否是物理地址（`pmemsave` 坏，不能用）。

## 7. P0bis 追加（2026-10-29）

### 7.1 SLA 4K60 的推算

- `rate=60000` → 帧周期 **16.6667 ms**（硬值）。
- active pixels = 3840×2160 = 8,294,400/帧 → active rate **497.664 MP/s**。
- `clk=0x11E1A300=300,000,000`：每帧 5,000,000 clocks；active pixels/clk = 1.659。若 2 px/clk，raw 600 MP/s、blanking ≈17.1%；若 1 px/clk，300 MP/s 不够，说明 300 MHz 不是最终像素率或字段是 PLL/参考时钟。**300 MHz 只标为候选，硬值只有 16.667 ms 和 497.7 MP/s。**
- 这是 3840×2160 的 8.29MP 视频窗口，不是全 DX 3936×2624。全 DX 60fps 需要 619.7 MP/s，超过这条 4K60 行；这解释了 4K60 为什么是裁切。
- 对目标档位：DX30 12-bit 309.8 MP/s = 4K60 视频 active 的 **62.2%**；C4 116.2 = **23.3%**；DX45 全 DX 464.8 = **93.4%**，但仍高于静止 12-bit 线 340.7（1.36×）。4K60 行不能证明“全 DX 45fps 可行”，只能证明视频路径在 8.29MP 窗口能到 497.7 MP/s。

### 7.2 P1 启动 trace 的解读

- 8 个运行期 SIF 入口只有 `0x1032C9C8` 命中 1 次，其余 7 个 0 命中。
- 说明启动阶段 SIF 入口不是模式配置路径（或只初始化一个通道）。P1 必须在菜单切换/拍摄时再跑；若菜单切换后仍只有这一个入口，说明配置不经过 SIF 入口，转 CAPTG/对象路径。
- 这次命中 `0x1032C9C8` 对应表项 17（SIF_5）；建议把该次的 `r0/r1/[r0+0xC]` dump 与启动后的对象注册表对照，确认它是否是传感器初始化的通道。

### 7.3 对象 arena 的结论

- `0xC2A49000` 全 0、`0xC188C000` 有数据 → 注册表指向的 `0xC188CC18..cc48` 是 **handle/descriptor**，不是对象本体；handle 里的对象指针（如 `0xC2A4AAB8`）落在 0xC2A4xxxx arena，启动时未初始化。
- 这不是地址错，最可能是**服务未启动/对象懒初始化**。先 dump `0xC2A40000 0x10000` 覆盖整个 arena；切换模式后再 dump 一次。若仍全 0，用 `xp` 验证指针是否是物理地址。
- 下一步优先试 **LV（APPLV）**：LV 会启动 capture pipeline，但不需要快门；进入 LV 后 dump `0x1242E4D0 0x400` 和 `0xC2A40000 0x10000`，看 CAPTG/SHUTTER 是否新增、0xC2A4A8xx 是否变非零。LV 不创建再试 Movie 模式；两者都不创建就标真机。
  - **已试（2026-10-29）**：LV 就是默认 APPLV，冷启动即存在（上传 300+），registry 仍 59 行、无 CAPTG；LV 不创建 CAPTG。Movie 模式不可切（物理拨杆），Release mode 无输入，外接快门 G14/G15 不触发。见 §9。

### 7.4 DX 切换结果（2026-10-29 主线）

- `registry_base.bin` vs `registry_dx.bin`：59 行、**0 dword 差异**；DX 切换不改变对象注册表。
- `arena_base.bin` vs `arena_dx.bin`：6020 → 6022 非零字节；4 B 差异在 `0xC2A45E04/0x14`、`0xC2A4BB90/91`，不在对象槽。
- `0xC2A4A000` 页 **0 非零**；非零页在 `0xC2A42000/45000/47000/48000/B000/C000/D000/E000/F000`。
- `0xC2A4A858` 和 handle 指向的 `0xC2A4AAB8` 都在零页/零槽；`0xC188CC18..cc48` 的 handle 也大多为空。
- 结论：DX 切换**不创建 CAPTG**；对象槽未初始化，不是地址错。下一步按 §7.3 先进 LV（APPLV），再试 Movie。

## 8. 菜单切换项（仿真机操作）

按固件字符串顺序（Photo Shooting Menu 第 1 页）：

1. **Image size** → `Large` / `Medium` / `Small`；DX 下分别对应 3936×2624 / 2944×1968 / 1968×1312。
2. **Choose image area** → `FX` / `DX`（同页还有 5:4、DX 24x16，不要选）。
3. **NEF (RAW) recording** → `NEF (RAW) bit depth` → `12-bit` / `14-bit`；压缩选 `Lossless compressed`。
4. **Release mode**：Z6 II **不在 Photo Shooting Menu 里**；官方操作是按住 **c/E（Release Mode/Self-Timer）按钮 + 旋转主指令拨盘**，再按 OK。第 1 页没有它是正常的。QEMU 按键表目前只暴露 MENU/OK/方向键/外接快门，没有 c/E 或主指令拨盘；若模型也没有，Release mode 标真机探针。

每改一项后退出菜单，dump `0x1242E4D0 0x400` 和 `0xC2A40000 0x10000`，对比是否有新条目/非零对象。重点看 CAPTG（任务索引 53）和 SHUTTER（54）是否出现。

## 9. 最终收口（2026-10-29）

- **LV 是默认 APPLV**：冷启动取景 HUD 持续存在（上传 300+），registry 仍 59 行无 CAPTG → LV 不创建 CAPTG。
- **Movie 模式切不过去**：Z6 II 拍照/视频是物理拨杆，模型无输入；Movie Shooting Menu 只是菜单页，不启动采集管线。
- **Release mode**：c/E 按钮 + 主指令拨盘，模型无输入。
- **外接快门 G14/G15**：pad 注入不触发拍摄，G15 只产生 +28 UI 事件。
- **DX 切换**：registry 0 差异，arena 4 B 噪声 → 不创建 CAPTG。
- **结论：CAPTG 需要实际拍摄序列；仿真机无法创建，标真机探针。** 仿真机路线到此为止；下一轮只在真机有数据时继续。
