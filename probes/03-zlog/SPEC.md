> ### 地址口径（重要，先读这段）
>
> mas 模块的**运行期基址是 `0x10020000`**。本文与本项目所有逆向笔记里出现的 `0x103Bxxxx`/`0x103Cxxxx`
> 这类地址，是**显示口径 = 文件偏移 + `0x10000000`**（`capd.py` 的 `BASE` 就是这个值）。
>
> ```
> 运行期 VMA  =  文件偏移 + 0x10020000  =  显示口径 + 0x00020000
> ```
>
> **给 QEMU / gdb 下断点必须用运行期地址（+0x20000），否则打不中。**
>
> | 用途 | 文件偏移 | 显示口径（本文写法） | 运行期 VMA（断点用） |
> | --- | --- | --- | --- |
> | 保存到卡入口 | `0x3BBDD4` | `0x103bbdd4` | `0x103DBDD4` |
> | NP3 序列化器 | `0x3BB862` | `0x103bb862` | `0x103DB862` |
> | 曲线表 rev16 | `0x3BC792` | `0x103bc792` | `0x103DC792` |
> | TLV 扫描（tag 2 / len 0x242） | `0x3BB6DA` | `0x103bb6da` | `0x103DB6DA` |
> | 打开成功返回码 helper | `0x4B6710` | `0x104b6710` | **`0x104D6710`** |
> | 两处打开状态 `cmp` | `0x3BA5F4` / `0x3BB70C` | `0x103ba5f4` / `0x103bb70c` | `0x103DA5F4` / `0x103DB70C` |
> | 卡载扫描入口（断点候选） | `0x3BB7B4` | `0x103bb7b4` | **`0x103DB7B4`** |
> | 槽位枚举（断点候选） | `0x3BB64E` | `0x103bb64e` | **`0x103DB64E`** |
>
> 一处需回报的换算差异：helper 的运行期地址按公式是 **`0x104D6710`**，不是 `0x104F6710`
> （后者相当于把 `+0x20000` 加了两次）。已用反汇编定位：文件 `0x4B6710` 处确有
> `ldr r5,[pc,#0x264]` 取到 `0x043A0089` 且随后 `subs r5,#9`，与描述完全吻合；而文件 `0x4D6710`
> 处是一段 `ldrd/strd` 数据拷贝代码，不含该常量。
>
> 另注：`np3_emu_probe.py` 用 `BASE=0x10000000` 建映射，属显示口径；它模拟的是模块内部自洽的
> PC 相对取指与 `snprintf` 实参，**结论与运行期基址无关**，因此文件名 `PICCON01.NP3` 的取证结果不受影响。

## 1. 定位与硬边界

ZLOG8 是 **Z6 II 机内可用的 8-bit 对数记录格式**，结构仿 RED/R3D 惯例（18% 灰卡为 Stop 0、
幂律趾部 + 对数主段、段间一阶连续），参数按 8-bit 载体重新标定。

它取代本项目此前的「机内 N-Log」目标，原因是固件侧已定论的硬边界：

- Z6 II 机内只有 H.264 8-bit。固件内 `HEVC` / `H.265` / `10-bit` / `Main10` 字符串零命中，
  也没有 Z8 那套 777 项 `eDSID_Setting_*` 里的 `H265Mov10bitToneMode`、
  `ProRes422Hq10bitToneMode`、`HlgQuality`、`MovieFrameSizeMov10bit`。
- 固件内**不存在** N-Log 曲线：256/257/1024/1025/4096 点 × 10/12/14/16-bit × raw/max 归一的精确
  字节指纹全部 0 命中；3608 段 ≥200 项单调表做仿射拟合 N-Log 形状亦 0 命中。
- N-Log 解析常数 0.328 / 650 / 619 / 0.0075 / 452 / 17.7 的 f32/f64 指纹在 Z6 II、Z7 II 全 0。
  Z8 有 `17.7`(f64) 与 `452.0`(f32) 但同样没有静态曲线表 —— 说明 N-Log 由运行时解析式生成，
  Z6 II 既无表也无这套解析入口。

结论：**真 10-bit N-Log 无法在 Z6 II 实现**（缺的是编码器位深与 ToneMode 框架，不是某个开关）。
ZLOG8 是在这块硬件上可获得 Log 工作流的全部空间。

## 2. 管线拓扑与输入/输出契约

```
[机内]  传感器线性 --BT.709--> Picture Control 曲线(ZLOG8) --H.264 8-bit--> MOV
                                                     |
[主机]  8-bit ZLOG8 帧 --decode(解析逆)--> 线性 X --+--> Rec.709 监看
                                                     +--> 16-bit TIFF 线性
                                                     +--> ACEScg(AP1) / ACES2065-1(AP0)
```

| 环节 | 输入 | 输出 | 位深/域 |
| --- | --- | --- | --- |
| 机内编码 | BT.709 显示域码值 0..255 | ZLOG8 码值 16..235 | 8-bit，video range |
| `curve_lut_256()` | — | 256 项整数表 | 8-bit 显示域逐码值采样，供核对与主机侧快速查表 |
| `curve_norm_257()` / `curve_be16_257()` | — | 257 项 / 257×BE16 | **这才是 NP3 曲线块内容**（0..0x7FFF） |
| `zlog8_to_linear()` | ZLOG8 码值 | 场景线性 X | float，X=1.0 为 clip |
| `zlog8_to_rec709()` | ZLOG8 码值 | 709 显示域 0..1 | 监看/预览 |
| `zlog8_to_aces(ap1=T/F)` | ZLOG8 码值 (N,3) | AP1 或 AP0 线性 | 含负值，不截断 |

契约要点：

- **机内曲线作用在 709 显示域，不是线性光**。所以交付的 256 点表是 `encode(bt709_eotf(in))`，
  而非直接对 X 采样。这是最容易做错的一环。
- X 的定义是「场景线性亮度 ÷ 视频满量程」，`X = 1.0` 即 clip 点。8-bit 机内链路**没有高光
  headroom**，因此规范不给 X>1 留码值——这一点与 10-bit 外录格式（N-Log 可编到 14.7 倍白）不同。
- 位深固定 8-bit，量化 16..235（video range），色度抽样 4:2:0。

## 3. 曲线定义

`X` = 场景线性 / 满量程；`x` = 8-bit ZLOG8 码值。

**正向**
```
if (X <= 0.050)
      x = 16337.2 * X^2.1030 + 16
else
      x = 63.0898 * ln(X) + 235
end
```

**逆向**
```
if (x <= 46)
      X = ((x - 16) / 16337.2) ^ (1 / 2.1030)
else
      X = exp((x - 235) / 63.0898)
end
```

**常数**

| 符号 | 值 | 含义 |
| --- | --- | --- |
| `C_BLACK` | 16 | 黑位 pedestal |
| `X_TOE` | 0.050 | 趾部/对数段交界（Stop −1.85） |
| `C_TOE` | 46 | 交界码值 |
| `C_TOP` | 235 | 满量程码值 |
| `LN_K` | 63.0898 | 对数段 ln 系数 |
| `P_TOE` | 2.1030 | 趾部幂指数 |
| `K_TOE` | 16337.2 | 趾部幅度系数 |
| `S_STOP` | 43.73 | 主段 code/档 |

`P_TOE` 由 C¹ 连续条件唯一解出：`P_TOE = LN_K / (C_TOE − C_BLACK)`。实测交界左右导数同为
**1261.7950**，比值 1.000000（见 `VERIFY.md`）。指数 2.103 与 N-Log 的三次趾部同族。

**锚点**（Stop 以 18% 灰卡 = X 0.18 为零点）

| 参考点 | X | Stop | code | IRE |
| --- | --- | --- | --- | --- |
| 黑 pedestal | 0.000 | — | 16 | 6.3% |
| 趾末 | 0.050 | −1.85 | 46 | 18.0% |
| **18% 灰卡** | 0.180 | **0.00** | **127** | **49.7%** |
| 亮调 | 0.300 | +0.74 | 159 | 62.4% |
| 满量程 clip | 1.000 | +2.47 | 235 | 92.2% |

## 4. 量化预算与动态范围

| 区段 | X | 档数 | code | code/档 |
| --- | --- | --- | --- | --- |
| 趾部 | 0 → 0.05 | ≈5.0（压缩） | 30 | 非均匀 |
| 对数主段 | 0.05 → 1.0 | 4.32 | 189 | **43.73** |
| 合计 | 0.0015 → 1.0 | **9.4** | 219 | — |

- 主段严格等步长：实测每 +1 码值的 stop 增量标准差 **2.07e-16**，即真对数段。
- 机内曲线把 256 级输入映射到 190 个唯一输出值，因此必然产生 **66 个平台**
  （恒等式：平台数 = 输入级数 − 唯一输出值数）。其中 23 个在趾部、43 个在主段。
  这是 8-bit 载体的信息论下限，不是曲线缺陷。
- 直接照搬 N-Log 形状到 8-bit 会得到约 26 code/档、149 个平台；ZLOG8 重标定后为 43.73 与 66。
- 量化闭环相对误差：主段 max **0.79%**、median 0.38%；趾部 median 1.89%。

## 5. 色域与白点

| 项目 | 取值 |
| --- | --- |
| 白点 | D65（由原色重算 XYZ = 0.950456 / 1.000000 / 1.089058） |
| 记录色域 | ITU-R BT.709 |
| 还原目标色域 | BT.709 / ACEScg(AP1) / ACES2065-1(AP0) |
| 位深 / 量化 | 8-bit / video range 16..235 / 4:2:0 |

**为什么是 BT.709 而不是 BT.2020**：Z6 II 机内没有 2020 通路。固件里 `2020` 的 8 处命中全部落在
LCD 点阵字模数据区，`HLG` 零命中。规范若声明 BT.2020，会诱导后期朝一个机内不存在的色域做还原，
产生系统性偏色。灰卡与镜面白的**参考点惯例**继承 RED，但色域诚实反映载体能力。

ACES 换基矩阵由原色坐标现算（不抄表），并与公开值交叉验证：BT.709→AP0 最大偏差 **9.13e-05**。

## 6. 与 N-Log / REDlog 的能力边界

| | ZLOG8 | N-Log v1.0.0 | REDlog Gen4/5 |
| --- | --- | --- | --- |
| 位深 | 8 | 10 | 10 |
| 色域 | BT.709 | BT.2020 | — |
| 灰卡 code | 127 (50%) | 372 (36%) | ≈37% IRE |
| 黑位 code | 16 | 127 | — |
| 高光 headroom | 无（X≤1） | 到 14.7× 白 | 到 1.85× 白以上 |
| 主段形式 | `63.0898·ln(X)+235` | `150·ln(y)+619` | log10 主段 |
| 趾部形式 | `X^2.103` | `(y+0.0075)^(1/3)` | 幂 toe |
| 段间连续 | C¹（解析导出） | 不连续（已知折角） | — |
| 有效档数 | 9.4 | ≈14 | ≈15–16 |
| code/档 | 43.7 | 104 | — |
| 载体来源 | 自定义曲线/NP3，可卡载 | 机内 ToneMode（Z6 II 无） | 机内 |

差异全部来自 8-bit 重标定。ZLOG8 不能套用官方 N-Log→REC.709 LUT，也不与 RED 工具链互通。

## 7. NP3 载体结构（真实样本实测版）

> **重大更正（2026-10-30）**：本节此前内容基于纯静态推断，其中三项是**错的**。
> 现已用本地真实样本 `work/color/tmpout/card/PICCON219.NP3`（1234 B）与 color 线参考解析器
> `work/color/z6ii_np3.py`（只读，未修改）实测校正。

| 旧记录（错） | 真实值（实测） |
| --- | --- |
| 文件头是 `u32 LE 0x043A0080` magic，再接 `"NCP\0"` | **偏移 0 就是 `"NCP\0"`**；`0x043A0080` 是打开成功返回码，不是魔数 |
| 把样本的 1234 B 当成通用容器 | 1234 B 是**扩展布局**；v1.70 自己导出的是**原生 834 B**（`0x342`），见 §7.5 |
| 曲线是 **256** 项 | **257** 项（`0x242 = 0x40 + 257×2` 精确成立） |
| 值域假定 **0..65535** | 满量程 **0x7FFF**（15-bit）；样本实测 1285…29298 单调 |
| 「块尾余出 2 字节用途未定」 | 那 2 字节就是**第 257 个点**，不是校验字段 |
| 版本是 `u16 BE` | 版本是 **ASCII 4 字节**（`0x10100` tag 的 body `"0210"`），版本门要求前缀 ∈ {01,02} |

`0x043A0080` **不是魔数，而是「文件打开成功」的返回码**：`0x104B6710` 处 `ldr r5,[pc,#0x264]`
取到 `0x043A0089`，`subs r5,#9` 后成功路径返回 `0x043A0080`；`bl 0x104B67A8` 之后的
`0x103BA5F4` / `0x103BB70C` 两处 `cmp r0,#0x043A0080` 检查的是打开状态。真实文件头只有 `NCP\0`，
所以在 NP3 样本里搜不到该常量是完全正常的——此前把它当魔数是误判。

**真实容器模型**（`np3_gen.py` 已按此重写，产物与样本可互相解析）：

```
"NCP\0"
TLV 流，每项 {BE32 tag, BE32 len, body}，按出现顺序：
  0x0100  版本      len 4   ASCII "0210"；0x103ba814 版本门要求前缀 01/02
  0x0200  名称      len 20  latin-1，NUL 结尾
  0x0300..0x1600   标量      len 2   (value, step)；固件 TBB 表只覆盖到这里
  >0x1600          被"读长度并跳过"（0x103ba7b2）——Z6II 不消费
  0x10100 说明文本  len 248
  0x0002  tone curve len 0x242  —— 放最后
BE32 = 0
```

标量约束（来自 color 线归纳的固件证据）：`0x0400` 的 value 必须 <3、`0x0500` 的 step 必须 ==1、
`0x0600` 的 step 必须 ==4；违反会被拒。

**曲线块 578 字节布局**：

| 区 | 字节 | 内容 | 置信度 |
| --- | --- | --- | --- |
| 块头 | `0x00..0x07` | `49 30 00 ff 0a e4 01 00` | 高（样本原样；但 `0ae4`/`0100` 字段含义未确认） |
| 元数据/锚点 | `0x08..0x3F` | `06 00 00 2e 16 62 55 9c a4 e4 ef ff` + 补零 | **低**：疑为锚点摘要，具体编码未完全逆出 |
| 曲线 | `0x40..0x241` | **257 个 BE16**，`round(norm × 0x7FFF)` | 高（样本实测 + `0x103bc792`） |

生成器默认**复用真实样本的 64 字节块头**（`--from-sample`），而不是自己拼——因为元数据区语义尚未
完全确认，照抄已确认可被相机接受的字节最稳。`--no-sample` 时才退回按 color 线算法生成锚点摘要。

其余仍然成立的结构性结论：

| 字段 | 值 | 置信度 | 证据 |
| --- | --- | --- | --- |
| 装载路径 | `B:\NIKON\CUSTOMPC\PICCON01.NP3` … `PICCON99.NP3` | 高（模拟执行实测） | §7.1 |
| 槽位 | 内置命名区 `0xC8..0x12A`，index = slot − 0xC7 | 高（模拟执行实测） | §7.1 |
| 盘符 `'A'/'B'` | 改写**路径字符串首字符**，与文件内容无关 | 高（模拟执行实测） | §7.2 |
| 尾随 BE32 == 0 | 必须 | 高（样本实测） | 尾部 4 字节全零 |
| 无校验和 | NP3 内部未见 checksum 计算 | 中 | 导出器 `0x103bb862` 全程无校验运算 |
| 卡载扫描链可达性 | 在本固件内**未找到任何入口** | 见 §7.4 | 六种引用方式 0 命中 |

**署名合规**：模板样本的 `0x10100` 里是第三方版权说明文本，生成器**默认替换**为 ZLOG8 自己的说明
（`--no-desc-replace` 可关闭，不建议）。产物不得携带他人版权声明。

### 7.1 文件名（确定）

扫描入口把路径交给 `0x103dc844`（snprintf 包装），格式串 `%s%s%02d.%s` 的四个实参经模拟执行为：

| 实参 | 值 | 来源 |
| --- | --- | --- |
| a1 | `B:\NIKON\CUSTOMPC\` | 字面量 `0x103bb8f8` |
| a2 | `PICCON` | 字面量 `0x103bb458` |
| a3 | 1…99 | `slot − 0xC7`，即 `0xC8→01`、`0x12A→99` |
| a4 | `NP3` | 字面量 `0x103bb454` |

→ 扩展名是 **`.NP3`**（不是 `.NCP`，也不是 `.pcx`；固件里根本没有 `.pcx` 字面量，
`NCP` 只出现在文件头标签）。实测样例：`B:\NIKON\CUSTOMPC\PICCON01.NP3`。

`0x12B..0x148`（30 个）走另一分支，用运行期记录里的自定义名（格式 `%s%s`，取记录 `+4` 与 `+0x17`），
那是相机导入后自己命名的槽——**我们不用管**，把文件放进 `PICCONnn.NP3` 即可。
`slot >= 0x149` 直接返回失败。

大小写：固件产出的字符串全大写且正好是 8.3 名（`PICCON01` + `NP3`），照抄即可。FAT 层对 8.3
名做大写规范化，小写**通常**也能匹配，但没必要赌——用大写。

### 7.2 盘符 `'A'`/`'B'` 的真实语义（确定）

`0x103bc77e` 的语义是：

```
bl 0x104e9568        ; 查询当前活动卡槽
cbz r0 -> 'A'        ; 否则 'B'
strb r0, [r4]        ; r4 = 传入缓冲区首地址 = 路径字符串的第 0 个字符
```

也就是说它把 snprintf 里硬编码的 `"B:\..."` 的 **`B` 覆盖成实际盘符**。
**加载路径完全不检查文件内容里的 A/B 字节**——我们生成的 `ZLOG8.NP3` 里不需要写任何 A/B 标识，
只要把文件放在**相机当前活动那张卡**的 `\NIKON\CUSTOMPC\` 根目录下。
QEMU 里对应哪个盘符由挂载的卡镜像决定，`vvfat` 只需保证文件在镜像根路径。

### 7.3 扫描的前置条件（若能进入该路径）

```
103bb7cc: ldr r6,[0xc188b2a4-0xc]
103bb7d0: ldr r0,[r6,#0x14]
103bb7d2: cbz r0, -> 继续扫描     ; 非 0 则整个函数直接返回 0
```

`[r6+0x14]` 是「本次已导入过」标志，成功导入时由 `0x103bb844` 置 1 → 每个菜单会话只扫一次，
重进界面才复位。**该标志恒 0 恰恰说明扫描从未被调用**（见 §7.4），而不是扫描失败。

### 7.4 ⚠ 卡载扫描链在本固件内**不可达**（实测取证）

对 `0x103bb7b4`（构造 `PICCONnn.NP3` 路径并读卡）做穷尽式引用搜索，五种方式全部 0 命中：

| 引用方式 | 结果 |
| --- | --- |
| Thumb `BL`/`BLX` 直接调用（全 MAS） | 0 |
| 绝对 dword / `dword+1`（MAS、SLA、ex1850、vr1850、tpj01 全扫） | 0 |
| `ADR`/`ADD PC` 相对（.text 全量扫描） | 0 |
| `MOVW #0xb7b4` + `MOVT #0x103b` 配对 | 0（MAS 里 `MOVT #0x103b` 一条都没有） |
| `BL` 目标落在 `0x103bb7a0..0x103bb7d8` | 0 |

而 Picture Control 的 UI 簇 `0x102d6xxx` 实际调用的函数是：
`0x103b84aa 0x103b89dc 0x103b8a0a 0x103b8b0e 0x103b90ce 0x103b91c8 0x103b99a0`
`0x103bb604 0x103bb64e 0x103bbfbe 0x103bbffe 0x103bc0ac 0x103bc11e`
——**没有** `0x103bb7b4`，也没有从文件解析的 `0x103bb4ca` / `0x103ba5ba`。

列表枚举函数 `0x103bb64e` 读的是运行期 RAM 表（基址 `0xc29925e8`，stride 8，99 项，值为 1 才算已导入），
以及记录 `+0x54` 的 u16。那张标志表只能由扫描/导入动作填充。

→ 因此：**卡里的 `PICCON01..99.NP3` 一个都不会被读到**，列表只显示内置项、
`[0xc188b298+0x14]` 恒 0、Manage Picture Control 无响应，三者是同一根因的三个表现。

不确定性：对话框也可能经服务/消息间接触发（非直接 `bl`）。决定性的 5 分钟检验是在 QEMU 里对
`0x103bb7b4`（**运行期 `0x103DB7B4`**）下断点后进入该对话框——若 PC 从不命中，即坐实。

绕过办法（可在 QEMU 内验证 UI 与曲线，不经卡片）：直接按记录布局写 RAM——
`0xc29925e8` 标志表置 1、`0x2a4` 记录（`+0x40` 起 256 项 LE 曲线、`+0x50`/`+0x54` 字段）、
并按 `0x103bb64e` 的判据填 `+0x54`。这样能回答「相机会不会列出并应用自定义 Picture Control」。

### 7.5 ⚠ 两种布局：v1.70 原生 834 B ≠ 样本的 1234 B 扩展布局

Z6 II v1.70 **自己导出到卡**用的是紧凑布局。证据链：`0x103BBDD4` 是保存到卡的入口
（内含 `B:\NIKON\CUSTOMPC\` 与 `%s%s%02d.%s`），它调用序列化器 `0x103BB862`（`movw r8,#0x242`），
后者依次写 tag `0x0100`…`0x1600`，然后在 `+0xF4` 写 tag `0x0002`、`+0xF8` 写 len `0x242`、
`+0xFC` 起 body，`+0x33E` 写 4 字节零尾，**总长 `0x342` = 834 B**。

| 偏移 | 内容 | 依据 |
| --- | --- | --- |
| `+0x000` | `"NCP\0"` | 标签 |
| `+0x004` | tag `0x0100` len 4，ASCII `"0210"` | 版本门 `0x103ba814` |
| `+0x010` | tag `0x0200` len 20，名称 | — |
| `+0x02C` | tag `0x0300`..`0x1600` **共 20 个**，各 len 2 `(value,step)` | `(0x1600-0x300)/0x100+1 = 20` |
| **`+0xF4`** | tag `0x0002`，len `0x242` | `4+12+28+20×10 = 244 = 0xF4` |
| `+0xFC` | body：`+0x00..0x3F` 块头/元数据 | — |
| **`+0x13C`** | **257 个 BE16 表** | `0xFC + 0x40` |
| `+0x33E` | 4 字节零尾 | `244+8+578 = 830` |

`PICCON219.NP3`（1234 B）多出的 `0x1700..0x1E00` 标量、`0x1F00`、`0x2000`、`0x10100` **不是 v1.70 写的**
（可能是别的机型或 PC 端工具）。但读取器按 TLV 扫描找 tag 2，所以扩展布局同样能载入。

**ZLOG8 产物默认按原生 834 B 生成**（`np3_gen.py --layout native`，即默认值），
`--layout extended` 可复现 1234 B 形态。标量区与 64 B 块头仍取自真实样本以保最大兼容。

**第 257 个点的字节序陷阱**：`0x103bc792` 的 rev16 循环是 `movw r4,#0x100` + `cmp r1,r4`，
即**只转前 256 个字**。第 257 个字不转换，因此它在相机内存里仍按文件的大端字节存在——
小端 CPU 读出的值会是字节交换后的数（例如文件 `0x75F5` → 内存 `0xF575`）。
文件里应写正确的 BE 值（与其余 256 点一致），但主机侧若按"内存语义"去读第 257 点，必须自己换回来。

**定标已完成**：真实样本已在本地，不再需要等相机导出。
