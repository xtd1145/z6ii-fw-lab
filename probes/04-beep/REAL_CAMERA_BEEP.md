# 真机可刷包说明 · 快门音工作流（2026-10-30）

> 本文件只描述**已生成的副本文件**。本轮不刷机、不写 NOR、不写卡。
> 刷写需你另行明确授权。K8 只经环境变量 `Z6II_K8` 传入，未写进任何源码或仓库文件。

## 0. 先说结论：这两个包都**不会发声**

从磁盘反汇编实测（不是读报告文字）：

```
beep5 stub @ f000d884 (16 B)：push.w {r0,r1,r2,r3,ip,lr}; bl 0x1073eafe; pop.w {...}; b.w 0x1073ecfc
beep6 stub @ f000d884 (24 B)：push.w {...}; push {r4,r5}; sub sp,#8; bl 0x1073eafe;
                              add sp,#8; pop {r4,r5}; pop.w {...}; b.w 0x1073ecfc
```

两个 stub 里都**没有 `bl BeepPlay`**，也没有任何 WAV 播放调用。它们只做一件事：
把快门释放点的 `bl` 换成 `b.w` 跳到跳板、在跳板里原样调用被调方、再把控制权还回去。

所以真机上的预期现象是：**不死机、快门行为不变、听不到任何新增声音**。
本轮能验证的是「相机是否接受自签容器 + 补丁是否 boot-safe」，**不能验证「静音拍摄下出声」**。

为什么没有有声包：`BeepPlay`（VA `0x10768b6e`）经 `0x10524005` 走**同步队列、超时 5000 ms**，
挂在快门释放上下文里有实测风险，已被判定弃用；唯一有社区实证的发声路径是 WonderLantern 的
卡上 `SHCORE` + `A:\SHUTTER.WAV`，尚未移植到 Z6 II。

## 2. 该刷哪个：建议 beep5

- **beep5**：注入 20 字节，栈只做 `push.w/pop.w` 一次，是三者里最小改动 → 首选。
- **beep6**：注入 28 字节，额外 `push {r4,r5}` + `sub/add sp,#8`。多出来的部分是**冗余但无害**
  （ARM 调用约定下 r4–r11 本就是 callee-saved，被调方不会破坏）。
- 注意 **beep6 与 `dist/noop6` 的 mas 字节完全相同**（sha256 同为 `fa494a68…`），
  两者不是「有声/无声」的差别，只是同一个镜像的两个名字。真正的差别只在 beep5（不碰 r4/r5、不留栈空洞）。
- **`from_d2_modcrc` 不出包**：它是故意改坏模块 CRC 的负样本，用于验证「相机会拒绝坏 CRC」。
- **已知会死循环的原始 `beep`/`noop`（`dist/beep`、`dist/noop`、顶层 `dist/EG185070*.BIN`）不出包**，
  它们 CPU0 停在 `0x101034fc` 自分支、GPU uploads 只有 12、HUD 仅 2111 字节 → 矩阵两级 FAIL。
  清空目录里那份 `DO-NOT-FLASH_Z6_2_0170_shutterbeep.bin`（原名 `Z6_2_0170_shutterbeep.bin`，已改名防误刷）就是这一版，**不要刷**。

## 3. 与原厂只差哪些字节（可自证）

容器层（密文）差异 42/50 字节，明文层分解如下，全部落在 mas 内 + 头部摘要：

| 层 | 偏移 | 原厂 | 补丁 | 说明 |
|---|---|---|---|---|
| 头 | `plain[0x00:0x14]` | `89019167…d3e4` | 重签值 | 唯一被改的头部字段；`plain[0x14:0x20]` 这 12 保留字节**原样保留** |
| 目录 | 5 项 `off/len` | 不变 | 不变 | 等长补丁，不动布局 |
| mas | `f000d884` | 全零（RPC 池稀疏区） | 跳板 16/24 B | 新代码 |
| mas | `f071ecf8` | `fff701ff` = `bl 0x1073eafe` | `eef4c4b5` = `b.w 0x1002d884` | 4 字节改链 |
| mas | `f24f47b8` | `8e61` | 重算值 | 模块 CRC16 |

其余 4 个模块（`ex1850`、`_tpj01`、`vr1850`、`eg1850_sla`）与原厂**逐字节相同**，已实测。

**一条重要推论**：包 CRC 恒为 `cf9a`——反证实验显示「只改 mas 载荷、不重算模块 CRC」会让包 CRC
变成 `a857`，而「改载荷 + 同步重算模块 CRC」又回到 `cf9a`。原因是每个模块段自带 CRC 使该段 CRC 贡献为 0，
包 CRC 只由段外结构决定。**所以包 CRC 无法区分原厂包与合法补丁包**；真正的校验关口只剩头部 SHA1
（我们已能自签）和那 12 个含义未知的保留字节。

## 4. 刷写步骤（需你明确授权后才执行）

1. **先留退路**：确认手上有原厂包 `Z6_2_0170.bin`
   （sha256 `5a9640b4c07abe1ecbf5a52655cbec6b893bba045bb2a1a1d21055b9f8f9d06d`）和
   NOR 备份 `.local/nor_candidate/NOR_64MiB.bin`（sha256 `f5fe8fabfd9d847a42dc924aedb20f026e4e960714a2086a5289220d10cf682f`）。
2. 取一张已在相机里格式化过的卡（**不格式化、不动 MBR/BPB**），把包按 Nikon 官方要求放到卡上
   （官方通用做法是卡根目录、文件名保持 `Z6_2_0170.bin` 形式；建议先把我方文件**改名**为该名后放置）。
3. 相机菜单 → 设定 → 「固件版本」，按提示执行更新。中途不断电、不拔卡、不按快门。
4. 更新完成后核对菜单里显示的版本号，并做一次实际拍摄（单张 + 连拍 + 静音拍摄各一次）确认不死机。
5. **本轮判定标准**：能刷进去 = 自签容器路径打通；不死机 = 跳板形状安全。**听不到声音属预期，不算失败**。

> 文件名与版本号的坑（未排除）：容器内模块名仍是 `eg1850_mas_01700`（= 1.70），
> 相机可能判定「已是最新」而拒绝更新；`Z6_2_017x.bin` 的文件名是否参与判定也未验证。
> 若被拒，先尝试改名/换版本号，而不是强行找绕过校验的办法。

## 5. 回滚

- **首选**：直接刷回原厂 `Z6_2_0170.bin`（同一条更新流程，向下/同级覆盖通常可行，但 Nikon 可能禁止降级——
  若被拒即转编程器路径）。
- **应急（有风险，需专门工具与明确授权）**：SPI 编程器把 `NOR_64MiB.bin` 整片写回。
  这会**写 NOR**，属于本 lab 的禁止项，只在相机已无法启动、且你明确授权时才做。
- 本工作流自身**从不写 NOR**：复核当日 NOR 镜像 mtime 仍为 `2026-10-19 15:27:50`、sha256 未变（见 `PROBE_SAFETY.md` §5）。
