# 电子快门音效：可改方案（2026-11-08）

目标：Z6 II 的电子快门（静音快门）按下去没有声音。要给它**加**一个可听、可换的音效。
本文只给方案与证据，不生成任何要刷的包。

## 1. 先确认一件事：固件里没有"电子快门音"这个开关

在 `eg1850_mas_01700` 里按 UTF-16 搜中文菜单串：

| 检索词 | 命中 |
|---|---|
| `电子快门` | 0 |
| `快门音` | 0 |
| `音效` | 0 |
| `静音拍摄` | 4（菜单：静音拍摄 开启/关闭，即电子快门） |
| `电子音設定` / `蜂鸣音` | 1 / 96（含 `音量 3 2 1`、`音调 高/低`） |
| `快门类型` | 1（自动/机械快门/电子前帘快门） |

也就是说，Z6 II 这一代固件**不提供**"电子快门音"菜单项；相机唯一的合成音源是
**蜂鸣音（电子音）**，它有自己的 `音量`/`音调` 设定。静音拍摄（电子快门）按设计就是
不出声的——不是打开某个开关就有了，只能"在释放路径上加一条播放"或"换掉音频资产"。

## 2. 固件里与声音有关的全部锚点

地址口径：file = 文件偏移；runtime = file + 0x10000000（显示口径 0x10020000 见
`z6ii-mas-address-convention`）。

| 对象 | file | runtime | 说明 |
|---|---|---|---|
| `BeepPlay` 包装函数 | `0x748B6E` | `0x10768B6E` | 无入参，内部固定请求 id=3；等待常量 `0x1388`；失败打日志 |
| `"BeepPlay failed."` | `0x748BC8` | `0x10768BC8` | 紧随其后，反查确认函数边界 |
| `"BeepPlay was timeout."` | `0x748BDC` | `0x10768BDC` | 同上 |
| 任务名表 `ShutterDrive` / `Beep` | `0x910580` | `0x10910580` | 两组 {ptr, name}，ptr 分别 `0xC1819B24` / `0xC181A30C` |
| `SoundEv0` | `0x386500` | `0x10386500` | 声音事件名，后随 `0xC1811B44` |
| `CSoundService` 类名 | `0x242D034` | `0x1242D034` | 类名表里的一员，说明有独立声音服务 |
| 内嵌 WAV | `0x18D5338` | `0x118E5338` | 见 §3 |
| cue 参数表（疑） | `0x18D5248` | `0x118D5248` | 12 B/条 `{序号, 采样数, flags}`，采样数 `0x1E20/0x1E40/0x4280` |
| `ShutterDrive request` 日志串 | `0x74B74D` | `0x1076B74D` | 快门驱动任务的请求/失败日志 |

`BeepPlay` 反汇编要点（`0x10768B6E`）：

```
push {r3-r7,lr}; r6=3; r4=r2(out); r0=3; bl 0x10524004   ; 发消息
r0=0; bl 0x10376c32; cbz -> 失败分支
movw r2,#0x1388; r1=sp; r0=3; bl 0x10524016              ; 等结果
失败/超时 -> 写 out、adr "BeepPlay failed."/"was timeout."、bl 0x104e35a2 打日志
```

它是**阻塞式**的（等待常量 0x1388），所以不能塞进中断或快门时序敏感点。

## 3. 唯一的音频资产：一段 60.0 s、48 kHz、16-bit、立体声 PCM

`file 0x18D5338` 是合法的 RIFF/WAVE：

```
RIFF size=0x00AFC824  WAVE
fmt  16 B: PCM(1), 2ch, 48000 Hz, byte-rate 192000, align 4, 16-bit
data size=11,520,000 B  -> 5,760,000 samples/ch = 60.000 s
```

- 数据本体 `file 0x18D535C .. 0x23D1B5C`。
- 这 60 s 里能切出 112 个非静音段（0.05–2.2 s），峰值打满 32768，
  过零率 0.002–0.39（音乐+噪声混合），更像**音效库/测试音轨**而不是单条快门音。
- 附近还有 `A:\TEST%04d.WAV`、`AudApEv3/AudApEv4/AudApSe0` 这类调试串，
  提示它可能是自检音源；**是不是快门音，必须在真机（或能触发播放的路径）上确认**。
- 全镜像只有这一个 RIFF；SLA、三组参数文件里都没有音频资产。

## 4. 三个可选方案

### S1 资产替换（推荐先做，风险最低）

把这段 PCM 换成我们自己的快门声（等长 11,520,000 B，48 kHz/16-bit/stereo）。

- 步骤：生成等长 PCM → 覆盖 `file 0x18D535C` → 重算 mas 模块 CRC 与包 CRC → K8 重签
  → 10 次 QEMU 冷启动 10/10 → 真机。
- 优点：不改任何代码路径、不改时序、不改菜单；出问题只会"声音不对"，不会崩。
- 前提：确认这段 WAV 就是快门/提示音源（§3 的未知项）。
- 变体：若只需要"电子快门有声音"，可以把整段换成"静音 + 在 0 s 放一声快门"，
  这样即使固件按偏移取片段，也总能听到。

### S2 cue 级替换（如果能找到 cue 表）

60 s 是音效库的话，找到"播放第 N 段"的接口，把电子快门路径改成播放快门段。

- 已知接口：`0x10524004`（发请求）/`0x10524016`（等结果），`BeepPlay` 就是它们的封装。
- 待定：cue 编号 → 偏移/长度的映射表；候选在 `file 0x18D5248` 附近，尚未证实。
- 验证路径：在 QEMU 里用**可达按键**（MENU/OK/方向）触发一次菜单音，
  hook `0x10524004` 记录参数；能记到就说明接口和 cue 编号都能在仿真里读出来。
- 优点：直接复用固件自带的快门声；缺点：要动代码，且需要先做一次仿真侦察。

### S3 注入 BeepPlay（能出声，但不是快门音）

在电子快门释放路径插一个 stub，调用 `BeepPlay`（固定 id=3）。

- 历史教训：beep6 的 stub 用了 `mrs/msr apsr`，目标核上不可用；beep6 最终把
  BeepPlay 整个删掉才做到开机安全（`probes/04-beep/beep6_report.md`）。
- 若要重做：stub 只保存/恢复 `r4/r5`，**不碰 APSR**；并且只能挂在任务上下文，
  不能挂在中断里（阻塞等待 0x1388）。
- 结果是一个蜂鸣提示音，不是机械快门"咔嚓"；好处是它遵守菜单里的 `音量`/`音调`，
  用户可以自己调。要快门音还是得走 S1/S2。

**听感路径的保留意见**：QEMU 建模的 audio DMA 是 "bank1 audio TX"，从寄存器看更像
HDMI/USB 音频输出，**不能证明机身有扬声器**。机身上能确认发声的只有蜂鸣音
（压电片）。所以 S1/S2 走 WAV 资产时，先确认这段 WAV 最终是从哪里出声的；
如果只走 HDMI，那么"电子快门音效"对拍照的人仍然听不见，S3 才是唯一可靠路线。

## 5. 怎么验证

| 环境 | 能做到 | 做不到 |
|---|---|---|
| QEMU | 开 `lab_audio=1`（`console.py` 会加 `laboratory-audio-dma=on` 和 `capture-file=audio-dma-capture.wav`），捕获固件真正推给音频 DMA 的 PCM | 按快门：仿真键盘只有 MENU/OK/↑↓←→，没有快门键；CAPTG 也不可达 |
| 真机 | 刷包后按快门录音，与注入的 PCM 逐段比对 | 目前不可用（2026-10-31 变砖待编程器） |

所以：**S1 在 QEMU 里只能验"开机不崩 + 资产被正确解析"**，声音是否真的在快门上响，
必须等真机。S2/S3 在 QEMU 里连"触发"都做不到（没有快门键）。

## 6. 建议顺序

1. 先用 S1 的"等长替换"做一版**只换声音**的包（不动代码），把它当基线：
   开机 10/10、菜单正常、无 Data Abort。
2. 真机恢复后，先确认这段 WAV 是否在快门时播放：
   播放一次快门并录音；若没声音，说明该 WAV 不是快门源，转 S2 侦察。
3. S2 只在拿到 cue 表之后做；S3 仅作为"必须有个提示音"的兜底。

## 7. 扬声器与视频播放链路（2026-11-08 静态定位）

### 7.1 证据链

| 层 | 位置 | 内容 |
|---|---|---|
| 设备注册表 | mas file `0x1896064..0x1896080` | 连续四个端点名：`HDMI`、`MIC`、`Speaker`、`EXTSB` |
| 服务名表 | mas file `0x242C614`、`0x242CBFC`、`0x242CD37` | `AudioApplication`、`AudioService`、`CodecService`（另有 `MoviePlayApplication`） |
| 硬件接口名 | mas file `0x76BBB6`、`0x76BBD6` | `AUDIO_IF_0`、`AUDIO_IF_1`（两个输出接口） |
| 驱动区 | mas file `0x36F000..0x371000` | `0x2C080000` 基址、`0x2C080110` 门控字面量、通道表；QEMU 注释记的 `0x1036FFA0/0x10370692` 就在这里 |
| DMA 端口 | QEMU 模型 | 通道目标只接受 `0x2C080104`（IF_0）或 `0x2C080204`（IF_1）；codec 门控读 `0x2C080110`/`0x2C080210` |

即：**放视频时的声音 = MoviePlay → AudioService → CodecService → audio DMA → codec → Speaker**。
码流本身是 48 kHz/16-bit/stereo PCM，和 §3 那段 WAV 的格式完全一致。

### 7.2 还没定的那一格

QEMU 模型两个端口都收、都写同一个 capture 文件，**不区分扬声器/HDMI**。
要确定 `AUDIO_IF_0` 与 `AUDIO_IF_1` 谁是 Speaker，只有两条路：

1. 真机放一段带声音的视频，hook `0x1036FFA0` 附近，记录通道 4..7 寄存器里的 target；
2. 把机器人的音频输出接到示波器/录音，逐个端口试。

真机自 2026-10-31 变砖，两条都做不了。**所以端口归属是当前唯一的功能性未知**。

## 8. 菜单侧的硬约束（决定"最稳妥方案"）

本项目 2026-10-28 的菜单实验结论（见 `z62-menu-model`）：

- ✅ 文案是**实时**从 mas rodata 读的；**等长**原地替换当场生效，无需重建、无纹理缓存。
- ❌ **加行不行**：运行期往页面容器 splice 节点结构上成立，但布局不重算，翻页/重开即被丢弃；
  持久加行要改"定义源"（疑似压缩资源），至今没找到。
- ❌ 同理，给一个下拉菜单**加第 4 个选项**也要改定义源。

所以用户要的两件事，可行性不同：

| 需求 | 可行性 | 最稳妥做法 |
|---|---|---|
| 菜单里出现"电子快门" | **高** | `静音拍摄`（4 字）等长换成 `电子快门`（4 字，UTF-16 各 8 B），共 4 处；动作一行不改 |
| 快门类型里加第 4 项 | **低** | 需要改选项定义源，不建议在真机恢复前做 |
| Z8 式自定义快门音（类型 A/B/C + 音量 + 音调 + 开关） | **中** | 复用现有 `蜂鸣音` 的 音量 3 档 / 音调 2 档，不加菜单行；A/B/C 只能做到 2 种 |

补充事实：**Z6 II 本来就有全电子快门**，就是 `静音拍摄`（photo 菜单 4 处文案：
`0x11F6464/0x11F647C` 帮助语、`0x11FDD04` 间隔拍摄、`0x1200C68` 报错语）。
它不是"电子前帘"，是全电子；只是没放进 `快门类型` 三选一里。

## 9. 定稿方案（按稳妥度排序）

### P1 菜单等长改名（先做，零结构风险）

把 4 处 `静音拍摄` 换成 `电子快门`，UTF-16 等长，不改动作、不改状态机。
效果：菜单里出现"电子快门"入口，点开就是全电子快门。包体只差这 8 个字节 ×4。

### P2 释放时播放 PCM（主体功能）

在快门释放钩子（已有 `CamCtl-InitiateCapture` file `0x74910C` / runtime `0x1076910C`）
里，按视频播放链的参数把一段 PCM 推给 audio DMA：

1. 先把 PCM 放在 DRAM 常驻区（`0xC2C00000..0xC5F00000` 内，已验证可写）；
2. 复用视频播放的通道初始化：`0x2C080000` 基址、`0x2C080104/0x2C080204` 目标、
   `0x2C080110/0x2C080210` 门控，48 kHz/16-bit/stereo；
3. 只播 100–300 ms，**不阻塞**（不调 BeepPlay 那种带 0x1388 超时的同步接口）；
4. 只在电子快门（静音拍摄）路径播，机械快门路径不播，避免"咔嚓 + 电子音"双声。

风险点：端口选错就只走 HDMI 不出声 → 先用 P0 定端口；不能挂在中断上下文。

### P3 自定义选项（降级实现）

- 开/关：电子快门模式下是否播放（参数位）。
- 音量：直接读 `蜂鸣音` 的 3 档 → 增益 1.0 / 0.6 / 0.3。
- 音调：读 `蜂鸣音` 的音调 高/低 → 两套 PCM（"A 型 / B 型"）。
- 类型 A/B/C：**做不到 3 种**，除非 P4 成功。

### P4 真加菜单项（暂缓）

只有找到菜单定义源（压缩资源解包）之后才做；否则做出来的行会被菜单重建丢掉。
这是 Z8 式完整菜单（类型 A/B/C + 电子快门音开关独立一行）的唯一前提。

## 10. 验证边界

- QEMU 能验：P1 的文案显示、P2/P3 的开机 10/10、无 Data Abort、DRAM 写入不越界。
- QEMU 不能验：播放。仿真键盘只有 MENU/OK/方向，**按不了快门**；视频播放也没有片源。
  模型自带的 `trigger-beep` 只是设备自测，不经过固件。
- 真机：恢复后先放视频抓端口（P0），再按快门录音比对 PCM。

## 11. 补充：相机内部本来就有"静音静态"模式

mas file `0x32BD20` 附近的**拍摄模式名表**里，六个名字是：

```
Still        LvStill
StillSilent  LvStillSilent
LvMovieRec   LvMovie
```

`StillSilent` / `LvStillSilent` 就是"静音静态拍摄"（全电子快门）的正式模式名。
这说明：

- **不需要发明"电子快门模式"**；固件里已经有，而且有独立模式名和独立路径。
- 用户看到的"只有电子前帘"，是**菜单暴露**的问题，不是功能缺失。
- 所以"把电子快门加进快门类型菜单"最稳妥的实现是**绑定到已有的 StillSilent 开关**，
  而不是给 `快门类型` 增加第 4 个取值——后者要改参数空间和拍摄状态机，风险高一个量级。

`LvStillSilent` 的存在还说明实时取景下的静音静态也是现成的，快门音可以在同一个模式下播。

## 12. "新增电子快门选项"的阻断点（2026-11-08 复核）

按要求不碰 `静音拍摄`，改为在 `快门类型` 里新增第 4 项。为此做了三项扫描，结论是**当前拿不到选项定义源**：

1. **文案是连续字符串流，不是独立字符串**。`mas file 0x11FEDB0` 起是
   `…快门类型自动机械快门USB电力输送…` 一条没有分隔符的 UTF-16 流；
   第三项 `电子前帘快门` 根本不在这一段（它在 `0x11F91C8` 的按钮功能列表里）。
2. **没有任何绝对指针指向这些文案**。对 `0x111FEDB2/BA/BE`、`0x111F91C8`
   做 32 位指针扫描：0 命中；16 位偏移扫描是噪声（同值 106 次）。
3. **能搜到的菜单文本指针全是帮助句子**。全镜像有 1299 个指向
   `0x111F0000..0x11202000` 的指针，抽样全是带换行的帮助语
   （如 `0x11200144` = "镜头拍摄，请将拍摄模\n式更改为"），属于帮助系统；SLA 里也有 114 个
   同类指针，同样是帮助语。
4. NOR 资源组 `group32.bin` 是 **100% 全零**（1.5 MB 占位头），不是定义源。

这与 2026-10-28 的菜单实验结论一致：**行的文案可等长替换（已验证），但行/选项的
"定义源"（数量、顺序、值映射）不在 mas 明文指针体系里**。要新增第 4 项，只有拦截
菜单建模函数这一条路：定位建模函数 → 选项容器结构 → 值派发/写回点，再在建模时插入
`{label="电子快门", value=3}` 并让设置消费者接受 3。

在拿到这套结构之前，任何"加选项"的包都无法验证，也不应该出。

## 13. 菜单建模已定位（2026-11-09）

用 QEMU + gdbstub 硬件观察点（这个 QEMU 没有 HMP `watch`）把菜单行的构建链抓出来了。

### 13.1 行记录（主引擎 DRAM）

| 字段 | 含义 |
|---|---|
| `+0x00` | `0x00029b0c`（每条行都一样，类型/签名） |
| `+0x04` | `0x00240024` |
| `+0x10` | 控件 id，低 16 位 `0x1064` |
| `+0x18` | **文案指针**（运行期地址，指向 mas rodata） |
| `+0x1c` / `+0x20` | 文案字节长度（两份） |
| `+0x68` | 同一文案指针的副本 |

实测标题行 `PLAYBACK MENU`：`ptr=0x110AEB9A` → file `0x108EB9A`，len 26；
`Delete` 12、`Playback folder` 30、`Playback display options` 48、`Image review` 24……
行记录在 `0xC2CF6408` 起、步长 `0x118`，B 记录在 A+0x50；两次启动地址一致。

### 13.2 构建函数

- **行填充函数：`0x1073EAFE`**（file `0x71EAFE`，`push.w {r4-r8,lr}`）。
  入参 `r0` = 解析器状态，`r1` = 行。它按 `[r5+0xc]` 的类型分支，
  通过 `0x107405F0` 等一组成员函数从序列化流里取字段，再写到行上。
- **行模板表**：`0x10740366` 返回一个全局指针，`r0 = 表基址 + index*16`，
  每条 **16 B**，按字节/字拷到行的 `+0xc/+0xe/+0x12/+0x5c/+0x44/+0x48/+0x40`。
  全局指针在 `0xC1D60B58`（`[G+0xc]`），由 `0x1074035E` 写入——**运行期装载，不是镜像里的静态表**。
- 观察点抓到写入 `0x00029B0C`（行首字）的 PC 在 `0x1073ED34` 附近（QEMU 归属 ±几条指令）；
  在关闭菜单后再下点会抓到堆复用的链表节点（`0x1034BFxx`），必须在**开机后、开菜单前**下点。

### 13.3 结论与下一步

- 行/选项不是代码硬编码，也不是镜像里的静态指针表；它们由**运行期装载的序列化定义**驱动。
- 要把"电子快门"加到 `快门类型`，需要在定义装载后追加一条（或在解析器层注入），
  不能靠改 mas 文案或加指针。
- 下一步：在菜单打开的状态下 dump `0xC1D60B58` 这组全局，顺着表指针找到定义 blob，
  解出记录格式（文本 id/长度/索引），再决定是改 blob 还是 hook 解析器。

## 14. 菜单定义的真正来源：压缩资源（2026-11-09）

顺着解析器全局 `0xC1D60B58` 往下，链路是：

```
G+0x00 = 0x10C10BBC  -> mas file 0xBF0BBC  指针表（12+ 个）
G+0x04 = 0x10C10C1C  -> mas file 0xBF0C1C  平行的"解压后大小"表
G+0x08 = 0x1094C048  -> mas file 0x92C048  另一组指针表（8 B/条的小结构）
G+0x0C = 0xC2029694  -> 运行期 RAM 缓冲（16 B/条的行模板表；本页全 0，与实测行字段一致）
```

- `0xBF0BBC` 表里的每个指针都指向一个以 ASCII **"hif"** 开头的块；
  `0xBF0C1C` 的对应项是它的解压尺寸（如 `0x0005D147`、`0x0001326F`）。
  这就是固件的**压缩资源表**。
- 菜单行/选项不是静态指针表、也不是代码常数，而是**从这些压缩资源解压后由解析器建出来的**。
  行首那个恒定的 `0x00029B0C` 是解析器给行写的类型字，不是镜像里的常量（全镜像只在
  三张偏移表里出现过同值，均与本函数无关）。

**结论**：要真正新增第 4 个选项，只有两条路：

1. **改压缩资源**：解开 "hif" 块 → 在定义里加一条 → 按原算法重新压缩。需要先逆出
   "hif" 编解码；这是纯静态工作，可以在 QEMU 外完成。
2. **解压后打补丁**：hook 解压完成点，在 RAM 缓冲里追加一条。需要知道记录的完整格式
   （文本 id/长度/索引/模板下标），并且要保证开机零副作用。

下一步先做 1 的解码器识别（"hif" 块头），因为它同时能给 2 提供格式信息。

## 15. 解析器初始化与"静态风格表"（2026-11-09）

用观察点抓 `[G+0xC]`（`0xC1D60B64`）的写入者：

```
HIT pc=0x10740364 lr=0x10637CBF val=0xC2029694
```

- 写入者 `0x1074035E` 只是 setter；调用者是 **`0x10637C3E`** 的解析器初始化函数。
- `0x10637CB8: ldr r0,[pc,#0x15c]` → 字面量 `file 0x617E18 = 0xC2029694`，
  再 `bl 0x1074035E`。也就是说 **16 B 行风格表放在固定的 RAM 地址 `0xC2029694`**，
  不是每次分配；我们抓到时它是全 0，与实测行 `+0x40/+0x44/+0x48` 为 0 一致。
- 同一函数在 `0x10637C98..0x10637CAE` 建了一张 0x12C（300）项的表；
  `0x10637C46/4A/52/5A…` 分别把镜像里的几组表地址写进全局 `G+4/G+8/…`。

全局 `G=0xC1D60B58` 的最终取值：

| 槽 | 值 | 镜像位置 | 形态 |
|---|---|---|---|
| `G+0x00` | `0x10C10BBC` | file `0xBF0BBC` | 指针表 → 48 个以 `hif` 开头的块 |
| `G+0x04` | `0x10C10C1C` | file `0xBF0C1C` | 平行的解压尺寸表 |
| `G+0x08` | `0x1094C048` | file `0x92C048` | 指针表 → 8 B/条的小结构 |
| `G+0x0C` | `0xC2029694` | 固定 RAM | 16 B/条行风格表（本页全 0） |

即：**行 = 解析器（`0x1073EAFE`）+ 序列化定义 + 固定风格表**；风格表在 RAM 固定地址，
定义来自带 `hif` 魔数的压缩资源。全镜像 `hif` 出现 48 次，没有"hif"常量的比较点
（说明加载器不校验魔数或用了别的判定）。

### 仍未解出

`hif` 块的压缩格式（头部字段、熵编码/字典）还没逆出来；这是"新增选项"最后一道门。
下一步：定位解压函数（从 `0x10637C3E` 里的调用链往下，或从 `hif` 块头部字段反推），
解出一份定义并确认记录格式。

## 16. 解析器状态布局（2026-11-09，断点实测）

在 `0x1073EAFE` 下断点，r0 = 解析器状态、r1 = 行对象头（r1-8 是对象头，
行记录在 r1+8）。每行一份状态，8 个字：

```
state: [0]=0x152B  [1]=0x0F   [2]=0x15F   [3]=1
       [4]=0x00A60048  [5]=0x00D602BE  [6]=1  [7]=0
row:   [0]=state_ptr  [1]=0xC2C37430  [2]=行记录  [3]=行记录
```

逐行实测（Playback 第一页，按构建顺序）：

| state[0] | state[2] | state[4] | state[5] |
|---|---|---|---|
| 0x152B | 0x15F | 0x00A60048 | 0x00D602BE |
| 0x1569 | 0x7B9 | 0x00DA0048 | 0x010A02BE |
| 0x1532 | 0x35C | 0x010E0048 | 0x013E02BE |
| 0x1535 | 0x174 | 0x01420048 | 0x017202BE |
| 0x1547 | 0x524 | 0x01760048 | 0x01A602BE |
| 0x1539 | 0x178 | 0x01AA0048 | 0x01DA02BE |
| 0x156C | 0x164 | 0x003E0048 | 0x006E02BE |
| 0x153C | 0x35F | 0x00720048 | 0x00A202BE |
| 0x1555 | 0x49B | 0x00A60048 | 0x00D602BE |
| 0x0067 | 0x157 | 0x0008004E | 0x003002B8 |

可以看出 `state[5] - state[4]` 恒为 `0x30`（48），`state[4]` 低 16 位恒 `0x48`（72）——
更像"版面/停靠位"参数，不是文本长度。文本指针（行 `+0x18`）是在这一函数之后由别的
代码写进去的（我们此前在这个槽上先抓到 `0x00029B0C`，随后才变成 `0x110AEB9A`）。

**结论**：解析器状态字段已拿到，但"文本 id → 文本指针"的解析器还没定位；
这是新增选项的最后一道门。

## 17. 卡点：文本 id → 文本指针的解析器（2026-11-09）

- 行构建函数入口断点可用：`0x1073EAFE`，r1 = 对象头，行记录 = `r1+8`，
  文本槽 = `r1+0x20`（= 行记录 `+0x18`）。
- 想"在第一次命中断点时对 `r1+0x20` 动态下观察点"被 gdb 拒绝
  （`Cannot use watchpoints in breakpoint commands`），批量脚本走不通。
- 固定地址 `0xC2CF6420` 的观察点在两次启动里命中过，但换一次启动就可能落在别的对象上，
  不能作为稳定手段。

要继续这一步，需要**交互式 gdb**（人工单步/条件断点），或者改用 QEMU 插件式 trace；
两者都不是本会话里能一次跑完的。至此菜单侧的可达边界是：

```
行记录字段 / 行构建函数 / 解析器状态 / 风格表 / 资源表 / 压缩块表   全部已定位
文本 id → 文本指针的解析器                                          未定位（最后一道门）
```

在没有解出这一层之前，"新增电子快门选项"不能出包，10 次冷启动也不会开始。

## 18. 语言表集合枚举完毕（2026-11-09）

每条消息 `start = base + off[i]`、`len = off[i+1]-off[i]`。当前语言（英文）的表在
`0xC1D60B68`（`[+0]`=table1 `0x116C1FFC`，`[+8]`=table2 `0x116C1F6C`）。

它决定快门类型页里有几个选项、值怎么映射。

### 18.1 新标签的落点

- 简体中文块 **没有空槽**（零长度消息 0 条）。
- 4 字（8 B）消息有 **328 条**，但都对应现有 UI 文案；直接覆盖会改动别的标签。
- 语义最接近的 4 字消息是 **1641 `静音拍摄`**——但用户明确要求不动它。
- 结论：要给新选项一个"电子快门"标签，只能
  ① 覆盖一条**确认不再使用**的 4 字消息（等长、不动池结构），或
  ② 在语言池尾部追加字符串并扩展偏移数组（会动到相邻数据，风险高）。
