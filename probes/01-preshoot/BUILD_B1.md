# B1-v2 · 用相机自己的“复制到存储卡”把探针数据带出来

v1（借 Picture Control 曲线块）在真机上被证明走不通：相机自建的用户优化校准**没有 tone
curve**，存出来是 248 B 无曲线文件；从卡载入曲线文件要么进不了列表，要么载入后曲线被丢弃。
v2 不再依赖曲线或载入：钩住相机的**写卡 API**，把每次保存的 248 B 文件直接当成数据块。
**4 次保存 = 一整页 864 B 的 STATUS+RING。**

| 项 | 值 |
|---|---|
| 容器 | `work/preshoot_build/Z6_2_0170_preshoot_np3.bin` |
| 尺寸 | 49,002,888 B（与原厂一致；mas 38,750,136 B） |
| 签名 | K8 重签，头摘要 `8d96b792f76e72ba4680716f456525ced670cc4c`；包 CRC `cf9a` |
| 文件 sha256 | `188e5efad750a730…` |
| 钩点 | 文件偏移 `0x4B68E6`（运行期 `0x104D68E6`，写卡 API 入口） |
| 解码工具 | `work/preshoot_build/np3_chunk_decode.py` |

---

## 1. 机制

相机保存 Picture Control 时，序列化器把 248 B（无曲线）或 0x342 B（有曲线）的 NP3 缓冲
交给写卡 API `0x104D68E6`。v2 只在这个入口、且同时满足以下条件时改缓冲：

1. 写入长度 == `0xF8`（248 B，无曲线 PC 文件）；
2. 写卡对象的路径以 `PICCON96.NP3` … `PICCON99.NP3` 结尾（**四个保留槽位**）；
3. 数据缓冲首字 == `"NCP\0"`，且容量字段 ≥ 0xF8。

任何一条不满足就原样放行——照片写入、设置写入、启动期重写、其它 95 个槽位都不受影响。

命中后，248 B 缓冲被替换成：

| 偏移 | 字段 | 说明 |
|---|---|---|
| +0x00 | u32 magic | `0x4450365A`（'Z6PD'） |
| +0x04 | u8 chunk | 0..3（由槽位号决定：96→0, 97→1, 98→2, 99→3） |
| +0x05 | u8 total | 4 |
| +0x06 | u16 len | 232（chunk 0..2）或 168（chunk 3） |
| +0x08 | u32 offset | chunk × 232 |
| +0x0C | u16 sum | 数据的 16 位累加和 |
| +0x0E | u16 version | 1 |
| +0x10 | 数据 | STATUS+RING 的对应切片（共 864 B） |

数据源固定为 `0xC5EFF000` 起的 864 B：STATUS 96 B + RING 768 B。

> 写出的文件**不再是合法 Picture Control**（内容被探针数据替换），只用于拷回电脑解码；
> 不要拿它去“载入”。相机保存流程本身不受影响（写完后不再读回内容）。

## 2. 用户操作（4 次保存）

1. 刷入本包（同尺寸、K8 重签）。
2. 拍几张照 / 正常使用，让 STATUS/RING 有内容。
3. 管理优化校准 → 载入/保存 → **复制到存储卡** → 选任意一个用户优化校准，槽位 **96**。
4. 同一个优化校准，依次再存到槽位 **97、98、99**（四个槽位各存一次）。
5. 把卡上 `NIKON\CUSTOMPC\PICCON96.NP3` … `PICCON99.NP3` 四个文件拷回电脑。
6. 解码：

```bash
python work/preshoot_build/np3_chunk_decode.py PICCON96.NP3 PICCON97.NP3 PICCON98.NP3 PICCON99.NP3
```

预期：每个文件 248 B、头 magic `5A 36 50 44`、chunk 0..3、sum ok；合并 864 B 后打印
STATUS 的 magic/count/frozen/retained/jpeg_hits… 与 RING 描述符。

> 不需要曲线、不需要从卡载入、不需要额外 PICCON 文件；卡上原来的用户优化校准不会被改动
> （96–99 是保留槽位）。

## 3. 为什么 v1 被废弃（真机实测）

- 相机自建用户优化校准导出 **248 B**：`NCP\0`、version `0300`、22 个 tag、**无 tag 0x0002**，
  到 `+0xF4` 结束（序列化器的无曲线分支）。
- 把带曲线块的 834 B（相机自己的 tag/数值 + 样本曲线）放进 `PICCON03`，相机**能载入**，
  但再保存出来仍是 248 B、且与相机原文件同 sha——**曲线在载入/保存往返中被丢弃**。
- 1234 B 扩展样本放进 `PICCON02` 时相机列表里直接“找不到”（v1.70 只认紧凑布局）。
- 结论：无法在相机上得到“带曲线且能再保存”的用户优化校准，v1 的曲线块导出不可行。

## 5. 限制

1. **每页需要 4 次保存**（同一 PC 存到 96/97/98/99）。保存到别的槽位不会产生数据块。
2. 写出的 248 B 文件不是合法 PC，**不要载入**；它只是数据载体。
3. 相机如果在写完后校验/回读文件，可能提示保存失败，但文件已写出；以卡上的文件为准。
4. 数据是导出瞬间的 STATUS+RING；连拍/预拍摄要多次采样时，重复 4 次保存即可。
5. 槽位 96–99 是保留位；如果你原来的卡上有这几个文件，先备份。

## 6. QEMU

```bash
python work/boot_one.py work/preshoot_build/Z6_2_0170_preshoot_np3.bin --tag preshoot-chunk
```

2026-10-30 实测 PASS：`guest=2.41 up=304 rnd=290 px=37 cpu0=10107094 wall=150.4s`，
无 Data Abort。启动期写卡不命中 96–99，`np3_writes` 保持 0。

## 7. 写目标

只写 `work/preshoot_build/` 下的副本。运行期写：

* DRAM `0xC5EFF000..0xC5EFF400`：STATUS / RING（数据源与计数）；
* 相机自己的写卡缓冲（`0x104D68E6` 的 descriptor 指向的 248 B），**仅当**路径是
  `PICCON96..99` 且长度 0xF8 且首字 `NCP\0` 时；
* 相机随后把该缓冲写到卡上的 `NIKON\CUSTOMPC\PICCON96..99.NP3`（相机原有的保存动作）。

不刷 NOR、不碰分区表与卡引导扇区。
